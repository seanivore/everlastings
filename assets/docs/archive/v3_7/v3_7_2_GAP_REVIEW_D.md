## 1. Ranked gap list

### #1 — [LOAD-BEARING — visual render defect] The new sale top-bar pushes the sticky header down on first paint, and the sale popup's (plus the pre-existing mobile-nav drawer's) fixed offset doesn't account for it — both visually collide with the header until the shopper scrolls

**Location**: `v3_7_2_IMPLEMENT.md` §4.3.c (`mountSaleChrome`, `assets/js/main.js`) + §4.3.d (`.sale-pop` CSS, `assets/css/styles.css`) — both NEW v3.5 code, DESIGN §D.2 — vs. the pre-existing `assets/css/styles.css:309-311` `.mobile-nav{position:fixed; inset:var(--header-height) 0 0 0;}` vs. `.site-header{position:sticky; top:0;}` (`styles.css:215-217`).

**What's wrong.** §4.3.c inserts the new `.sale-bar` as the literal first child of `<body>` — `document.body.insertBefore(bar, document.body.firstChild)` — genuinely in normal document flow, ahead of `.site-header`. I confirmed `<header class="site-header" data-site-header>` is body's first real element (only comments precede it) on every storefront template (`index.html:98`, `shop.html:98`, `product.html:99`, `checkout.html:99`), and `body{display:flex; flex-direction:column}` (`styles.css:118-130`) stacks children in DOM order — so on a fresh, unscrolled page load, `.sale-bar` sits above `.site-header`, pushing it down by the bar's own height. `.site-header{position:sticky; top:0}` only pins to the viewport's top edge once scroll has carried it there — **before** that, it sits exactly where normal flow puts it (the code's own comment agrees: *"the bar sits in normal flow above the sticky header, so it scrolls away and the header THEN pins to top:0"*).

I computed the bar's actual rendered height from real, repo-verified tokens: `.sale-bar{padding:var(--space-sm) var(--space-md); font-size:var(--text-sm);}` = 8px top/bottom padding (`--space-sm:8px`, `styles.css:72`) + one line of 14px text at the global `line-height:1.6` (`--text-sm:0.875rem` `:56`, `--leading-normal:1.6` `:67`, inherited from `body`) ≈ 8 + 22.4 + 8 ≈ **38-39px**. So at initial load, `.site-header` (height `var(--header-height):64px` `:101`, plus its `1px` `border-bottom`) spans roughly **38px → 103px** from the viewport top, not `0 → 65px`.

`.sale-pop`'s `top` is a **static** `calc(var(--header-height) + var(--space-md))` = `64 + 16 = 80px` (`styles.css` new block, §4.3.d) — landing squarely inside the header's real (unscrolled) 38-103px span, about 42px into its ~65px height. Since `.sale-pop{right:var(--space-md); max-width:320px}`, the overlap lands specifically on the header's **right side** — where the cart icon sits on both mobile and desktop (per `index.html`'s own header-layout comment: *"Mobile: hamburger (left), logo (center), cart icon (right) / Desktop: logo (left), nav (center), cart icon (right)"*). The popup is `z-index: calc(var(--z-modal)+10) = 210`, confirmed above the header's `var(--z-header):100` (`styles.css:95`), so it renders **on top of**, not hidden behind, the header — a visible collision, not an invisible one.

The pre-existing `.mobile-nav{position:fixed; inset:var(--header-height) 0 0 0;}` drawer (unrelated to this build, but a component this build's new bar now conflicts with) makes the **identical** unstated assumption — its top offset is also just `--header-height`, with no accounting for a bar above the header. Tapping the hamburger while unscrolled and a sale is active would open the drawer starting ~38px too high, overlapping the header's lower band the same way.

**Confidence**: computed from real, repo-verified CSS custom-property values (not a live render) — flagging per "flag, don't assert": browser subpixel rounding could shift the numbers a few px, but not enough to close a ~23px overlap. This is exactly the class of bug that a single-token existence check (what B-fidelity + my own v3.7.1 pass both did — confirming `--header-height`/`--space-md`/etc. all *exist*) can't catch, because the defect is in the **arithmetic across** several correct tokens, not in any one token being wrong or missing.

**Concrete fix**: don't hardcode the popup's `top` (or the drawer's `inset`) against `--header-height` alone — read the header's actual live bottom edge at mount/open time, which is correct in both the unscrolled (bar-present) and scrolled (bar-gone, header pinned) states without any new CSS token:
```js
const headerEl = document.querySelector('[data-site-header]');
const top = headerEl ? headerEl.getBoundingClientRect().bottom + 16 : 80; // fallback
pop.style.top = top + 'px';
```
Apply the same idea to `.mobile-nav` if the hamburger can plausibly be tapped before the shopper has scrolled (it can — it's the very first interaction on a fresh mobile visit). This is a bounded, single-mechanism fix (one measurement, reused for both), not a redesign.

**Load-bearing vs polish**: **LOAD-BEARING (visual)**. Not a functional break — the popup stays on top and dismissible, the drawer still opens — but it's a genuine "renders wrong" defect (the review lens's own named failure class) that recurs on **every** fresh storefront visit for as long as a store-wide sale is active and unscrolled, colliding with the header's primary cart-icon navigation on the surface WS4 is built specifically to promote.

### #2 — [LOAD-BEARING-leaning-POLISH] D#6's scope-picker fix doesn't say whether the new `is_published` check ADDS to or REPLACES the picker's existing archived-exclusion — and I confirmed archiving never touches `is_published`, so the ambiguity has a real failure mode

**Location**: `v3_7_2_IMPLEMENT.md` §4.6 (the D#6 note) vs. `design-handoff/out/sales-app.js:11` (`const pickProducts = (D.products || []).filter((p) => !p.archived_at);`) vs. live `api/products.ts:906-911` (`handleArchive`'s DB update).

**What's wrong.** §4.6 says: *"the New-Sale scope picker must filter its piece list to published products"* — concrete on the WHAT (filter to `is_published`), silent on whether that's **additive** to the picker's current-shipped filter (`!p.archived_at`) or a **replacement** of it. I checked whether this distinction can actually matter — i.e., can a product be simultaneously archived AND `is_published:true` in this data model — by reading the live `handleArchive` (`api/products.ts:872-912`): its only mutation is `.update({ archived_at: archive ? new Date().toISOString() : null })` — **it never touches `is_published`**. This is corroborated elsewhere in the same build: the WS6 storefront-gate pattern at `products.ts` (referenced in IMPLEMENT around the series/sold-recovery checks) explicitly ORs both conditions — `product.is_published !== true || product.archived_at != null` — which would be redundant if the two flags were coupled. So an archived piece genuinely CAN retain `is_published:true` (e.g., a maker archives a still-live piece directly, without unpublishing it first).

If a builder implements §4.6's instruction as a literal filter-to-published (`.filter(p => p.is_published)`), replacing rather than ANDing with the existing archived check, an archived (Stripe-mirrored `active:false`, meant-to-be-invisible, per ledger 12 "revivable, not deleted") piece would reappear as scopable in a brand-new sale — contradicting the whole point of archiving a piece.

**Concrete fix**: name the exact filter in §4.6, explicitly additive: `pickProducts = (D.products || []).filter((p) => !p.archived_at && p.is_published)` — one clause, removes the ambiguity entirely. (Minor, same location: unlike every other surgical WS4 fix in this doc — e.g., §1.4f's byte-anchored CURRENT/NEW block — §4.6's D#6 note is prose-only with no CURRENT/NEW pair; given the `pickProducts` anchor was already named in the pre-fold finding this fixes, a concrete one-line NEW block costs little and removes the guesswork this angle's charge explicitly flags — "a step where the builder must … guess.")

**Load-bearing vs polish**: leans POLISH — narrow trigger (requires an already-live piece to be archived directly, without a prior unpublish, which may be uncommon in practice) — but the fix is a single clause and cheap to make unambiguous now rather than risk a real "archived piece is sale-scopable" regression later.
