## 1. Gap list (ranked)

### #1 — `cart_holds` removal (WS7 Phase 7.2) reopens an unmonitored oversell race for one-of-a-kind pieces; the two STORE.md decision entries it reverses are never marked SUPERSEDED, and the risk gets no go-live/awareness note (unlike the build's other new production dependency, `CRON_SECRET`, which did)

**Location.** `v3_7_1_IMPLEMENT.md` WS7 Phase 7.2 (all of 7.2a–7.2i, lines ~2616–2816) + Phase 7.2i's Doc-impact line; `EVERLASTINGS_STORE.md` Key Architectural Decisions **#18** ("Availability check BEFORE any PII," line 203) and **#19** ("Soft cart holds, not hard reservations," line 205), plus the duplicate pair in STORE.md's own "Architecture Reference" section (items 28/29 there), the `cart_holds` schema table section, the "`is_test` isolation (all six core tables)" paragraph (becomes five), and the System Diagram ASCII listing `POST /api/checkout/reserve → availability + 15-min soft hold`.

**The system-fit gap.** WS7 Phase 7.2 removes the entire `cart_holds` reservation mechanism ("#224, pre-cutover" — return to the original no-reservation design) and correctly implements that removal cleanly: `handleSession`/`handleReserve` in `api/checkout.ts` keep their availability re-checks, the webhook's post-order hold-cleanup is dropped, and the `DROP TABLE` migration ships safely commented per the project's own destructive-op convention. I verified this against the current `api/checkout.ts` and `api/webhook.ts` directly — the removal is surgically correct and every CURRENT anchor I checked matches the tree.

But the mechanism it removes was the store's *only* protection against two shoppers concurrently buying the **same physical one-of-a-kind piece** (`quantity=1`). Traced end-to-end: Shopper A and Shopper B both add the same qty-1 piece, both hit `POST /api/checkout/reserve` (now a pure availability check — no lock), both pass (quantity is still 1, neither has paid), both get an independent Stripe Checkout Session for the *same* Stripe Price, both complete payment. Both webhooks fire as two distinct, legitimate Stripe events (different `event.id`, so the `webhook_events` idempotency claim does **not** dedupe them — idempotency there is per-event, not per-product). `record_sale` is atomic per row (verified — `supabase/migrations/20260616000001_v3_1_inventory_decrement.sql:26-38`, a single `UPDATE...FROM counts` statement, `greatest(qty-n,0)`), so it never corrupts `quantity` (first call 1→0, second call `greatest(0-1,0)`→0) — but atomicity here only protects the *counter*, not the *sale*: both `orders` rows get created, both buyers are charged, both get a merchant-notification email for the same product on the same day. Emy has no automated signal this happened; she'd have to notice two "new order" emails for the same item herself.

**This is not a build defect** — it's a deliberate, reasoned trade-off, already stated in `assets/docs/archive/v3_5/v3_5_0_ROADMAP.md:32`: *"The webhook never auto-refunded a true double-pay collision anyway → low-volume = negligible."* I'm not recommending reversing it — for this store's actual traffic, that reasoning is sound, and I confirmed the recovery path already works cleanly: the existing refund endpoint (`orders.ts` POST, unchanged by this build) lets Emy refund the extra sale with `relist_product_ids:[]` (no relist, no quantity bump), which correctly models "I'm refunding this money but keeping the item with the buyer who's shipping." **What's missing is detection, not resolution.**

Two things make this worth surfacing now rather than leaving it implicit in a v3.5 ROADMAP sentence: (1) this build adds `EVERLASTINGS_STORE.md`'s **only** other new production dependency in the same breath — `CRON_SECRET` — and that one *did* get explicitly promoted to a go-live checklist item (ledger 59/`v3_7_1_REVIEW_PROMPTS.md`) precisely because a silently-inert dependency is exactly the "hides without explaining" failure class this project's own thesis forbids; the cart-hold removal creates a structurally identical silent risk and gets no equivalent promotion. (2) This build adds a **new** money-integrity monitor — WS7 §7.3's reconciliation cron — which checks for "a paid Stripe session with no matching `orders` row." I traced `reconcileOrders()` (`api/product-feed.ts`, as this build writes it) line by line: it compares Stripe's completed-session list against `orders.stripe_session_id`. A double-sale produces **two** `orders` rows (one per session) — there is no missing row, so reconciliation is structurally blind to this exact failure mode. A reader could reasonably assume "money integrity is now watched" without realizing this specific class isn't covered by the new watcher.

**Concrete fix (cheap, doc + optional code):**
- Add one sentence to Phase 7.2i's Doc-impact (and the `EVERLASTINGS_STORE.md` go-live checklist, alongside the `CRON_SECRET` note) naming the accepted trade-off explicitly: no reservation ⇒ a narrow concurrent-checkout window remains for `quantity=1` pieces; low-volume-store risk, accepted; resolve via a normal refund with `relist_product_ids:[]` if it ever happens.
- Mark `EVERLASTINGS_STORE.md` KAD #18/#19 (and their AR-section duplicates) **SUPERSEDED** the same way this build already does for `data-flow.md:55` (ledger 20) — the project has a clean, established convention for this exact situation ("kept in context, not silently deleted"); it just wasn't applied here.
- *(Optional, not required)* `reconcileOrders()` could cheaply add a second check — flag `>1` completed order on the same `product_id` within its scan window where the product isn't multi-stock — reusing the same email path. A nice-to-have, not a blocker.

**Load-bearing vs polish:** load-bearing for the project's own "nothing hides without explaining" operator-transparency thesis, and for `EVERLASTINGS_STORE.md`'s role as the system-of-record — **not** load-bearing for code correctness (the code does exactly what WS7 specifies, correctly). This doesn't block execution; it's a fold-able doc addition (a few sentences), not a re-review trigger.

### #2 — GPT instruction `.txt` 12-byte headroom has a named fallback for one failure mode but not the plainer one

**Location.** WS10 Phase 10.5 (running byte budget, `v3_7_1_IMPLEMENT.md` lines ~3712–3719) vs. the §10.1c residual note (lines ~3631) and ledger entry 76.

**The system-fit gap.** The projected final byte count is exactly 7988/8000 — a 12-byte, 0.15% margin — built by summing four independently hand-authored prose deltas (Phase 10.2 `+263`, 10.2b `+10`, 10.3 `-28`, 10.4 `-44`). I independently re-added these (7787+263+10-28-44=7988) and the arithmetic is internally consistent, but hand-counting prose edits to exact-byte precision across four separate phases is inherently error-prone (a smart quote vs. straight quote, an em-dash vs. hyphen, one extra space — any of these silently shifts the count by a few bytes). The doc already has a named fallback for the *specific* case where the GPT-behavior test in TESTING item 6b fails (§10.1c's residual: "rework line 4... self-funded via §10.2b's freed clauses") — but that fallback is scoped to a *behavioral* test failure, not to the plainer scenario where the final `wc -c` simply comes in over 8000 because the hand-counted deltas were off by a handful of bytes. Phase 10.5 just says "over-cap = the GPT silently truncates its own instructions and the gate fails," with no named "trim target if over by N" the way the §10.1c residual has one for its own narrower concern.

**Concrete fix.** Name a trim target for the plain over-budget case too (e.g., "if the final count exceeds 8000, drop N more bytes from &lt;specific low-value clause&gt; first" — there's likely a few bytes of slack in the same phases that already trimmed themselves).

**Load-bearing vs polish:** polish. The static gate (both in IMPLEMENT and independently in TESTING's static-gate section) re-counts before ship either way, so this can never silently ship over-cap — it would just cost a short, unplanned trim-and-recount cycle at build time rather than having the trim pre-named.
