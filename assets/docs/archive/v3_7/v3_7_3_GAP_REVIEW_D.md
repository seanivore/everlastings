## 1. Ranked gap list

### #1 — [LOAD-BEARING] The media-modal half of the checkout-identity freeze (ledger 87, IMPLEMENT §5.4e) has no concrete lock spec — as written, a maker can toggle the frozen "Checkout" role, get a success toast, and have the change silently dropped

**Location**: `design-handoff/out/products-app.js:657` (`ROLE_DEFS`, includes `checkout`), `:666-667` (`mItemHTML`'s rolebox render — every role, including `checkout`, renders as a plain clickable pill with zero disabled/locked state), `:726-737` (`toggleRole` — no publish-state check anywhere; `checkout` toggles exactly like `share`/`poster`), `:745-763` (`applyMedia` — line `:760` unconditionally does `p.checkout_image = checkout.url` whenever a checkout-role item exists in `mItems`, then line `:762` fires `P.toast("Media updated", { kind: "live" })` unconditionally) — vs. `v3_7_3_IMPLEMENT.md` §5.4e ("on a published product the modal must (i) show the 'checkout' checkbox as locked (reuse the 'locks after first publish' lock-chip pattern, `out/products-app.js:274`) and (ii) not include `checkout_image` in the Apply `PUT` unless it's unchanged") and §5.4c.i (the Apply-diff algorithm: "`checkout_image` obeys Phase 5.4e's ever-published freeze... **skip the write** on any ever-published piece").

**What's wrong.** The editor-field freeze (slug/checkout_name/checkout_description) is protected two ways: the HTML `disabled` attribute makes it physically impossible to edit, *and* if a change somehow still reached the server, `FROZEN_AFTER_PUBLISH` 400s it. The media-modal's "checkout" role has **neither** protection specified concretely. §5.4e says to "show the checkbox as locked (reuse the lock-chip pattern)" but `lockChip()` (`out/products-app.js:274`) is designed to sit inside a `field__top` next to a text-field label — there is no CSS in `portal.css` for a locked *rolebox* (a checkbox pill, not a labeled text field), and IMPLEMENT never names one. Nothing in §5.4c.i or §5.4e tells the builder to guard `toggleRole()` itself, and nothing tells the builder that `applyMedia`'s **local-state mutation** (`p.checkout_image = checkout.url`, the line the mock already has at `:760`) must also be skipped when the terminal PUT skips it. So a plausible, even likely, implementation reading of "just omit `checkout_image` from the outgoing PUT payload" is: the client-side click on the "Checkout" rolebox still toggles normally (`toggleRole` has no guard), `applyMedia` still runs its existing `p.checkout_image = checkout.url` line (updating the in-memory model the editor immediately re-renders from), the modal closes with the existing unconditional "Media updated · live now" toast — and only the outgoing PUT quietly omits the field. The maker sees a picture of success. On the next full page load (or the next `GET /api/products?id=`), the server's true `checkout_image` reasserts itself and the maker's apparent change vanishes, with no toast, no red ring, no explanation — the exact "hides without explaining" failure class the brief and this project's own thesis explicitly rule out, and the same failure *shape* (client optimistically shows a change the server will never honor) that ledger 87's own §2.7a fix was written to close on the text-field side.

**Concrete fix.** Three coordinated pieces, all cheap and bounded (no redesign):
1. **CSS** — add a `.rolebox--locked` modifier (or extend `.rolebox` with a `[data-locked]` attribute selector) using the same visual language as `.field--locked` (dashed border, muted background/text, `cursor:not-allowed`) so a locked "Checkout" pill reads as intentionally frozen, not just inert.
2. **`toggleRole()`** — guard the `checkout` branch on `everPublished` (the same flag ledger 87 introduces for the editor fields): on an ever-published piece, refuse the toggle and toast `"Checkout image locks after first publish"` (mirrors the existing `toggleRole` pattern of toasting a rule explanation, e.g. its current "This is the hero — it can't also be a gallery image" message) instead of silently mutating `it.roles`.
3. **`applyMedia()`** — make the `p.checkout_image = checkout.url` assignment conditional on the same `everPublished` check the terminal PUT payload uses, so the client's own optimistic model never shows a change that didn't persist. If (2) is implemented correctly this becomes unreachable defense-in-depth, matching how the text-field side keeps both the `disabled` prevention *and* the server 400 backstop.

**Load-bearing vs polish**: **LOAD-BEARING.** This is a real, plausible-to-ship gap in exactly the mechanism my charge asked me to verify ("how does the maker SEE the freeze") — not a cosmetic nit. The failure mode (false-success toast, silent revert) actively erodes trust in the "auto-save on close, no warning" UX pattern this whole editor is built around (FEEDBACK §9): if one save-and-close can silently lie, the maker has reason to double-check every one.

### #2 — [LOAD-BEARING-leaning-visual] `.field--locked` — the CSS class the design addendum names as the concrete "locked" treatment — is defined in `portal.css` but never applied anywhere in `out/`; a locked editor field renders with only `disabled` + the lock icon, not the designed dashed/muted state

**Location**: `design-handoff/out/portal.css:328` — `.field--locked .input,.field--locked .select{background:var(--surface-sunk); color:var(--ink-muted); cursor:not-allowed; border-style:dashed;}` — vs. `out/products-app.js:276-292` (the `f()` helper that renders every editor field, including the three ledger-87 locked fields): the returned template is `` `<label class="field${span}"${ring}${rec}>...` `` — `span` is only ever `" ed-span2"` or `""`; `o.locked` controls **only** whether `lockChip()` renders and whether the control gets the `disabled` HTML attribute — it never adds `field--locked` (or any class) to the wrapping `<label>`. I grep'd the entire `design-handoff/` tree for `field--locked` and it appears **exactly once** — its own definition in `portal.css:328` — confirming this is genuinely dead CSS, not something I missed in another file. Cross-referenced against `v3_7_3_ADDENDUM_DESIGN.md` §C.1: *"Lock-after-publish = show locked, not missing (concrete — `portal.css` `.field--locked` + `.tip__btn--lock`)... render them **locked** (dashed, muted, `cursor:not-allowed`) with a lock icon..."* — the addendum's own concrete definition of "locked" is this exact class, and it doesn't render.

**What's wrong.** A locked field today shows: the lock-icon chip (with its hover/tap tooltip — this part works), and whatever the browser's own default UA styling does for a plain `disabled` `<input>`/`<select>` (commonly a subtle text-color dim, no distinctive border or background change). It does **not** show the intentional dashed border + muted background the addendum specifies as *the* signal that a field is "locked, not missing" rather than merely "disabled for some other reason" (loading, permission, etc. — states this same portal has elsewhere). This directly weakens ledger 87's very reason for existing: the fold's whole point is that a *paused* piece must visibly, unambiguously show its checkout fields as frozen — but the strongest available visual cue for that (the dashed/muted treatment) never fires, leaving the maker to infer "locked" from a small icon plus generic grayed-out text that could just as easily read as "this field hasn't loaded yet."

**Concrete fix.** One-line change to `f()`'s return template: `` `<label class="field${span}${o.locked ? ' field--locked' : ''}"${ring}${rec}>` ``. Since this ships in `out/` (the canonical byte-source) rather than being introduced by the IMPLEMENT integration seam, it should be folded into the same surgical-edit note ledger 87 already carries for `products-app.js:339`, or named as its own one-line surgical edit in DESIGN §A's list — right now nothing in the build docs instructs anyone to make this connection, so it will ship exactly as broken as it is in `out/` today unless caught here.

**Load-bearing vs polish**: leans load-bearing given it's the addendum's own named mechanism for a freshly-reworked freeze cue, but the field genuinely IS non-editable regardless (the `disabled` attribute + lock icon still function) — so I'm not calling this a functional break, just a fidelity gap against the addendum's own explicit spec.

### #3 — [POLISH, residual] `--header-offset` is measured once (on `mountSaleChrome` call + `window resize`), not on scroll — because `.site-header` is `position:sticky`, its true bottom edge shrinks once the sale-bar scrolls out of view, so a still-open sale-pop or a mobile-nav opened after scrolling can show a stale (too-large) offset

**Location**: `v3_7_3_IMPLEMENT.md` §4.3.c (`setHeaderOffset` — called once inside `mountSaleChrome`, then re-bound only to `window.addEventListener('resize', setHeaderOffset)`) vs. `assets/css/styles.css:215-217` (`.site-header{position:sticky; top:0; ...}`, confirmed live) vs. `assets/css/styles.css:309-311` (post-fold `.mobile-nav{position:fixed; inset:var(--header-offset, var(--header-height)) 0 0 0;}`).

**What's wrong.** `getBoundingClientRect().bottom` is viewport-relative (scroll-position-sensitive), and it's called exactly once at mount (plus on resize). At `scrollY:0`, `.site-header`'s real bottom edge is `sale-bar-height + header-height` (correct, matches what's stored). Once the shopper scrolls past the bar's height, `.site-header` — being `position:sticky; top:0` — pins to `y:0`, so its real bottom edge shrinks to just `header-height`. `--header-offset` is never re-measured for this (no `scroll` listener), so it keeps reporting the larger, stale, unscrolled value. Two concrete consequences: (a) if the sale-pop is still open (nothing auto-dismisses it on scroll) while the shopper scrolls, it — being `position:fixed` — stays pinned at its original larger offset while the header visually shrinks toward the top, opening a growing gap between them (not an overlap, so it doesn't reintroduce the original bug, just looks slightly adrift); (b) the mobile-nav drawer can be opened at **any** scroll depth (unlike the once-per-sale popup, this is a routine, likely-to-be-hit interaction), and would render with its top edge at the stale larger offset — a visible band of gap under the now-shorter header where neither the header nor the drawer's background covers, showing whatever page content is scrolled to that position through the crack.

**Concrete fix.** Either add a (rAF-throttled) `scroll` listener alongside the existing `resize` one calling the same `setHeaderOffset`, or — cheaper — recompute once, synchronously, at the moment the mobile-nav is toggled open (the drawer's own open-handler is a natural, low-frequency hook that avoids a scroll listener's performance cost entirely, and covers the higher-likelihood case).

**Load-bearing vs polish**: POLISH. This is strictly a narrower residual of an already-mostly-fixed bug — it degrades toward "gap" rather than regressing toward the original "overlap the cart icon" failure, and both trigger conditions (scrolling with the popup still open; opening the hamburger after scrolling while a sale is live) are real but not the primary/first-visit path the v3.7.3 fix was scoped to close.

### #4 — [POLISH] The New-Sale scope picker's empty-state copy doesn't distinguish "no such piece" from "piece exists but isn't published yet" — and the corrected additive filter (ledger 89) makes the broken literal-empty-quotes variant of that message reachable on first open, not just after a fruitless search

**Location**: `design-handoff/out/sales-app.js:150-165` (`renderPickList`) — specifically `:165`: `` list.innerHTML = rows.length ? ... : `<div class="picklist__empty">No pieces match "${esc(q)}"</div>`; `` — vs. `v3_7_3_IMPLEMENT.md` §4.6 (the ledger-89 additive filter).

**What's wrong.** Two related gaps in the same render path. First, whenever the picker is empty, the copy always reads as if a *search* came up empty ("No pieces match…"), even though after ledger 89's fix a piece can be entirely absent from the list for a structural reason (it's a draft — not published, so it has no `stripe_product_id` and can't be coupon-scoped) that has nothing to do with the maker's search term. A maker who knows a specific not-yet-published piece by name and searches for it in the picker gets the same "doesn't match" message as if the piece never existed, with no cue that publishing it first would make it appear. Second, and more concretely reachable: `renderPickList("")` is called on the picker's initial open (`openModal`'s `renderPickList("")` at `:135`) — with an **empty** query, so if `pickProducts` (now filtered to `!archived && is_published`) has zero rows — a realistic state for an early-stage or pre-launch catalog with nothing published yet — the maker sees the literal string `No pieces match ""` (empty quotes) the instant they toggle off "Whole store," before typing anything. That reads as a broken UI string, not a helpful explanation, and it's a state the corrected (stricter) filter makes materially more likely to hit than the picker's pre-fold behavior.

**Concrete fix.** Split the empty state into two copies: a genuine no-eligible-pieces state (`q` empty, `pickProducts` empty at the source — "No published pieces yet — publish a piece first to scope a sale to it") separate from the no-search-match state (`q` non-empty, filtered rows empty — keep "No pieces match "…""). Both are cheap, purely-client-side string branches in the existing function.

**Load-bearing vs polish**: POLISH. Doesn't block the "Whole store" path (the default), and a maker with any published inventory won't hit the empty-catalog variant — but it's a real, concrete, easily-triggered rough edge in a fold this round specifically touched.
