## Finding 1 — [LOAD-BEARING] The v3.7.3 lock-cue fix re-keys `slug` onto the wrong condition — a saved-but-never-published draft shows its slug as editable, invites an edit ("edit if you like"), and silently discards it

**Journey it breaks:** "Create a piece → fill fields → publish" — specifically the fill-fields phase, any time after the first autosave and before first publish.

**Where:**
- `v3_7_3_IMPLEMENT.md:119` (Locked decisions → "Editor field rules"): *"**Lock-after-publish** (show locked, not missing): `slug, checkout_name, checkout_description, checkout_image` — **the client lock cue keys on `everPublished = !!p.published_at`, NOT `is_published`** (v3.7.3, journey #1)."*
- `v3_7_3_ADDENDUM_DESIGN.md:44` (§A surgical-edit list): *"the editor's lock-after-publish fields (`slug`/`checkout_name`/`checkout_description`) compute their `locked:` cue off `everPublished = !!p.published_at`... matching the server `FROZEN_AFTER_PUBLISH` guard (§2.7a)."*
- `api/products.ts:359-360` (verified against the live tree): `if (Object.prototype.hasOwnProperty.call(updates, 'slug')) { return jsonResponse(request, { error: 'slug is immutable' }, 400); }` — this check fires **unconditionally**, on ANY `PUT` to an existing row that includes a `slug` key, **before** the function even inspects `current.is_published`. Slug is not in `FROZEN_AFTER_PUBLISH` (`api/products.ts:337-340` — `checkout_name, checkout_description, checkout_image, sku, stripe_product_id, stripe_price_id`); it is governed by a wholly separate, stricter, always-on rule: once a row exists (post-`POST`), slug can never be included in a `PUT` again, publish state irrelevant.
- `assets/js/admin.js:612-613` (the retired reference implementation Phase 2.1a explicitly ports): `const slugVal = $('p-slug').value.trim(); if (!state.editing && slugVal) payload.slug = slugVal;` — slug is added to the outgoing payload **only when creating** (`!state.editing`); on every edit of an existing row, it is silently omitted from the request body. `v3_7_3_IMPLEMENT.md:475` (Phase 2.1a) names this exact behavior: *"existing row → `PUT ?id=` (strip `slug` — it 400s as immutable, `products.ts:359`)."*
- `assets/docs/archive/v3_5/design-handoff/out/products-app.js:339` (verified against the live prototype): `const r = readiness(p), published = p.is_published, archived = !!p.archived_at;` and `:375`: `${f({ label: "Slug", ..., locked: published, field: "slug", ... })}` with tip text *"Auto-made from the title; edit if you like."*
- `api/products.ts:210` confirms slug IS settable at create (`const slug = slugify(rawSlug) || ...`), and the GPT schema (`v3_3_0_GPT_SCHEMA.txt:19-22`) requires it on `createProduct` but **does not expose `slug` at all on `editProduct`** (verified — its properties list has no `slug` key) — so this failure mode is structurally impossible on the GPT surface; it is portal-only.

**Concrete failure scenario:** Emaline starts a new piece in the portal, types a title + price. The moment she clicks away (auto-save-on-close), `autosave()` fires a `POST`, the row now has an `id`, but `published_at` is still `null` (it's only stamped at actual publish, `api/products.ts` first-publish branch). She keeps drafting over several sittings — the slug field renders **unlocked** the whole time (`everPublished` is false for the entire pre-publish life of the draft, same as the OLD `is_published`-keyed logic before this round's fix — the fold moved the same wrong condition, it didn't correct it for this one field), with its tooltip actively inviting an edit. She decides she wants a cleaner URL slug and retypes it. She saves. The field shows no error. On her next visit (or the next auto-save-triggered reload), the slug is silently back to the original value — no toast, no red ring, no explanation. This is precisely the "it just didn't work and didn't say why" failure the review lens targets, and it's worse than a 400 because there is no error at all — the edit is dropped before it ever leaves the browser.

**Why this isn't fully covered by the v3.7.3 fold, and why it's worth flagging now:** the fold's own text ("matching the server `FROZEN_AFTER_PUBLISH` guard") is accurate for 2 of the 3 fields it re-keys (`checkout_name`, `checkout_description` — genuinely governed by `FROZEN_AFTER_PUBLISH`, genuinely gated on ever-published) but is a category error for `slug`, whose real governing rule is "does this row already exist" — true from the moment of first save, independent of publish state. This round is the one that explicitly re-touches this exact bullet (re-keying from `is_published` to `everPublished`) and had a natural opportunity to give `slug` its own, correct condition instead of bundling it with the two `FROZEN_AFTER_PUBLISH` fields — it didn't, so the pre-existing bug (present since before this build too) survives the fold unchanged.

**The fix or the decision it needs:** give `slug` its own lock condition, independent of publish state — `locked: !!p.id` (or equivalently, "locked whenever this is not a brand-new, never-saved row") — so it shows locked the instant the first autosave creates the row, matching the moment `buildProductPayload` starts stripping it. Leave `checkout_name`/`checkout_description` on `everPublished` (that part of the fold is correct). One-line addition to `v3_7_3_ADDENDUM_DESIGN.md:44` and `v3_7_3_IMPLEMENT.md:119` to split the two conditions.

## Finding 3 — [POLISH] `--header-offset` is measured once at mount + on resize, never on scroll — after scrolling past the (always-present) utility bar, the sticky header's real bottom edge shrinks but the CSS variable doesn't follow

**Journey it breaks:** "Run a store-wide sale" — the header-clearance fix (D#1 / ledger 88), but the *scrolled* case rather than the unscrolled-load case the ledger explicitly closes.

**Where:** `v3_7_3_IMPLEMENT.md:1430-1435` (§4.3.c, `mountSaleChrome`'s `setHeaderOffset`): `setHeaderOffset(); window.addEventListener('resize', setHeaderOffset);` — no `scroll` listener. Verified against `assets/css/styles.css:215-217`: `.site-header { position: sticky; top: 0; height: var(--header-height); ... }` — once scrolled past the (normal-flow, always-present) bar, the sticky header pins at `top:0` with height exactly `--header-height` (the bar is no longer part of its box), but `--header-offset` — set once at load to "bar height + header height" — never shrinks to match.

**Concrete effect:** this is not the overlap bug D#1 fixed (that's genuinely closed — verified the unscrolled-load math is correct: `getBoundingClientRect().bottom` is read synchronously after the bar is inserted, before the popup/drawer CSS ever consumes the value). The residual is the opposite direction and cosmetic: if a shopper scrolls down past the bar and *then* opens the mobile-nav drawer, the drawer's top inset uses the stale, larger (bar-inclusive) offset, leaving a visible empty gap between the header and the drawer's top edge rather than a flush fit. Never a collision with the header or cart icon.

**The fix:** add `setHeaderOffset` to a scroll listener too (ideally throttled/`requestAnimationFrame`-gated), or accept the cosmetic gap as a known, low-priority render-tune item — not a build blocker either way.

## Finding 4 — [POLISH] The media-modal Apply-diff algorithm asserts, but never explicitly authors, the step that makes retries idempotent

**Journey it breaks:** "Media upload modal — a partial-failure mid-fan-out."

**Where:** `v3_7_3_IMPLEMENT.md` §5.4c.i, the "Partial-failure recovery" bullet (the block ledger 48/75 already close for the stop-but-still-PUT-partial-state behavior — this is a narrower residual in the same block). The parenthetical reads: *"(iv) DO NOT clear `mItem.openedRoles` on the failed item so the next Apply retries only the remaining diff (**the succeeded items now have `mItem.openedRoles` = their new state, so their diff is empty on retry** — a re-Apply is idempotent)."*

**The gap:** the bolded clause is stated as an already-true fact, but no bullet in the algorithm (the "on open" stash, the "on Apply" diff-compute, the "for each added role" / "for each removed role" writes) contains the actual positive instruction — update `mItem.openedRoles = new Set(mItem.roles)` for each item once its write succeeds. Only the negative case (don't clear it on the *failed* item) is explicit. Without that line, a retried Apply would recompute the SAME non-empty diff for items that already succeeded in the prior attempt, re-issuing an already-completed re-role POST.

**The fix:** one sentence in §5.4c.i — "after each item's write(s) complete successfully, set `mItem.openedRoles = new Set(mItem.roles)` so its diff is empty on any later Apply." Low risk of a builder getting this wrong (the described idempotent-retry behavior only works this way, so it's a fairly forced inference), but worth stating outright per this doc's own "exclusively executable" bar.
