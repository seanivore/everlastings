## Findings

### 1. [MODERATE, leaning load-bearing on the thesis] The v3.7.3 `everPublished` client re-key (ledger 87) bundles `slug` with two fields it doesn't share a server mechanism with — and the fix that lands doesn't actually fix `slug`

**Where**: `v3_7_3_ADDENDUM_DESIGN.md` §A's "WS2 lock-after-publish re-key" bullet (line 44) → `design-handoff/out/products-app.js:339,375` (the `editorHTML` function, `locked: published` on the `slug` field) vs. the live server `api/products.ts:337-340` (`FROZEN_AFTER_PUBLISH`) and `api/products.ts:359-361` (the unconditional slug-immutability check) vs. the CURRENT (pre-redesign) `assets/js/admin.js:321` (`$('p-slug').disabled = !!product`).

**The systems seam.** DESIGN §A's fold text says: *"the editor's lock-after-publish fields (`slug`/`checkout_name`/`checkout_description`) compute their `locked:` cue off `everPublished = !!p.published_at`... matching the server `FROZEN_AFTER_PUBLISH` guard (§2.7a)."* This is accurate for `checkout_name`/`checkout_description` — both are literally in the live `FROZEN_AFTER_PUBLISH` array (`api/products.ts:337-340`), so gating their lock cue on "has this piece ever been published" now correctly mirrors the server's ever-published-aware freeze. But `slug` is **not** in `FROZEN_AFTER_PUBLISH` at all. Its actual server rule is unconditional and unrelated to publish state: `if (Object.prototype.hasOwnProperty.call(updates, 'slug')) return jsonResponse(..., 'slug is immutable', 400)` (`api/products.ts:359-361`) — this fires on **any** `PUT` that includes the key, whether the row is a brand-new draft, paused, or live.

Re-keying `slug`'s lock cue to `everPublished` doesn't fix anything for it: on a never-published draft, `everPublished` is `false` (same as the old `published` cue was), so the field **still renders unlocked/editable** — even though `slug` has been immutable since the row's first save, and WS2 Phase 2.1.a's own integration instruction confirms the client already knows this ("existing row → `PUT ?id=` (strip `slug` — it 400s as immutable, `products.ts:359`)"). The practical consequence: a maker editing a draft's slug field types a change, saves, and the edit is **silently stripped before the PUT is even sent** — no toast, no error, nothing — which is exactly the "hides without explaining" failure class this build's own thesis (and this exact fold's own stated purpose, for the other two fields) is built to close.

The **current, pre-redesign** admin already gets this right and more simply: `assets/js/admin.js:321` — `$('p-slug').disabled = !!product` — locked whenever editing any existing row, full stop, independent of publish state. The redesign's `out/products-app.js:375` (`locked: published`, now `locked: everPublished`) is a regression from that parity baseline that predates this fold and that the fold doesn't close, despite bundling `slug` into its fix.

**Compounding gap — the coordination note wasn't updated either.** WS1 Phase 1.1a (line 155) is the doc's own canonical list of every named surgical edit later workstreams make to the verbatim-shipped `products-app.js`: *"WS2 miniature-only picker, WS8 Sold-tab alert removal, WS3 Delivered-pill removal, the `--staged` token fix — see DESIGN §A's surgical-edits list."* This v3.7.3 edit (the `everPublished` re-key) is not named there, unlike its four siblings **and** unlike the WS1 "View-Site href" fix (DESIGN §A, also new-ish) which IS cross-referenced back from a WS1 open-item note (line 437). The doc demonstrates the correct cross-referencing pattern elsewhere in this very build; it just wasn't applied to this specific fold.

**Fix**: give `slug` its own cue, not `everPublished` — e.g. `locked: true` (or `locked: !!p.id`, since the editor only ever opens a row that's been saved at least once) — separately from the `everPublished`-gated `checkout_name`/`checkout_description`/`checkout_image`. Add a one-line pointer in WS1 Phase 1.1a's surgical-edits list so the next reader finds this edit the same way they find its four siblings.

### 2. [MODERATE] The homepage featured carousel doesn't carry the same "sold-despite-available:true" lag-window fix that the sibling related-products surface got in the same workstream

**Where**: `v3_7_3_IMPLEMENT.md` §6.3d (`homepage.js` `populateFeatured`/`tile()`, ~line 2440-2460) vs. §6.5d (`product.js` related-products card, line 2589-2597) — both fetch with `getProducts({ ..., available: true })` (confirmed live: `assets/js/homepage.js:10` and `assets/js/product.js:539`).

**The systems seam.** `record_sale`'s atomic SQL always keeps `quantity=0 ⇒ available=false` together (migration `20260616000001`), so the normal automatic-sale path can never produce a fetched `available:true` row with `quantity<=0`. But WS2's own integration seam (`commitQty`, line 458: `PUT ?id= {quantity}` — live-apply, independent of the `available` toggle) means a maker **can** manually zero a piece's quantity via the row's inline quantity field without touching Available — reaching exactly that state: `available:true, quantity<=0`.

WS6 §6.5d (related products) explicitly anticipates and closes this for its own surface: its fetch is `available:true`-filtered, but its render still computes `(rp.quantity != null ? rp.quantity <= 0 : !rp.available)` and shows a Sold badge if true, with the comment *"Cosmetic — the related pool is fetched `getProducts({ available: true })`, so a click-through still hits the 6.5b buy-gate; this just closes the lag-window on the card badge."* — i.e., the author of this exact workstream already identified and fixed this precise class of gap once.

§6.3d (homepage featured), edited within the **same** workstream and fetching with the **identical** `available:true` filter shape, computes the identical `sold` boolean per-tile (line 2443: `const sold = p.quantity != null ? p.quantity <= 0 : !p.available;`) — but only uses it to **suppress** the Featured/Unique badges (`!sold && ...`). There is no `badge-sold` branch anywhere in the homepage tile template. So a piece in this exact edge state — featured, manually zeroed to `quantity:0` without toggling Available off — would render on the homepage carousel with **no badge at all** (not Sold, not Featured, not Unique) and a plain (non-struck) price, looking like an ordinary purchasable item, when clicking through correctly reveals it's sold (PDP + checkout both still block purchase — this is a **display-only** gap, not a buy leak).

TESTING item 30's own framing — *"the homepage shows... no 'Sold' (homepage fetches available:true)"* — treats the fetch filter as a sufficient guarantee, which §6.5d's own adjacent fix (in the same doc, same workstream) already disproves for the sibling surface.

**Fix**: add the identical Sold-badge branch to `homepage.js`'s `tile()` function, mirroring §6.5d's fix exactly — `${sold ? '<span class="badge badge-sold">Sold</span>' : ''}` ahead of the Featured/Unique gates (which already correctly exclude on `sold`). Cheap, one line, matches an existing in-doc precedent.

### 3. [MODERATE] The GPT's own shipped instruction text still teaches the pre-fold raw-snake_case `story_card` example that ledger 92 (snake_case-400 RESOLVED) was supposed to close on "BOTH surfaces"

**Where**: `v3_7_3_IMPLEMENT.md` §10.2b (lines 3686 **and** 3690 — both the CURRENT quote and the actual shipped NEW block for the GPT's `PUBLISHING:` instruction line) vs. WS2 §2.7's `FIELD_LABELS` map (line 863: `story_card: 'Story'`) vs. the ledger-92 text itself (*"validatePublishRules maps field keys to plain labels (FIELD_LABELS) in the 'Missing required fields' 400 on **BOTH surfaces**"*) vs. `v3_7_3_ADDENDUM_TESTING.md`'s own revision note (line 5: *"the publish-400's plain-words example now uses the mapped label (item 6b — snake_case-400 RESOLVED, fold #10)"*).

**The systems seam.** This is a directly provable, byte-level inconsistency between two artifacts in the same triplet. WS10 §10.2b's actual GPT instruction NEW block — the text that **ships verbatim, unparaphrased, into Em's Custom GPT** per this workstream's own explicit rule ("The instruction file ships verbatim from the CURRENT/NEW blocks below — do not paraphrase") — still reads:

> `A publish 400 ("Missing required fields: story_card" / "Minimum 5 gallery images") = say plainly what to add (story_card = the story, headline = the tagline).`

Post-fold, the server never emits `story_card` in that message anymore — `FIELD_LABELS` maps it to `"Story"` before the 400 ships (confirmed: `story_card: 'Story'` is one of the map's 12 complete key→label entries, verified by enumeration against every possible `missing.push()` target in `validatePublishRules`). So this worked example, which the GPT is taught **verbatim** as its model of what a real 400 looks like, is now describing a string the server will never actually send.

The TESTING addendum's own revision note explicitly claims this exact class of staleness was fixed this round ("the publish-400's plain-words example now uses the mapped label") — and it's true for TESTING's **own** illustrative example (item 6b now correctly says `"Missing required fields: Care instructions"`) — but that fix didn't propagate to the actual production artifact (the GPT `.txt`) carrying the identical pattern.

**Practical severity (flag, don't assert):** an LLM-driven GPT is not a literal string-matcher — it receives the REAL tool-call response body (now correctly saying `"Story"`) and the general instruction "say plainly what to add" would likely still produce a sensible reply regardless of the stale worked example. I can't verify the actual runtime GPT behavior from here (no ChatGPT access), so I'm not asserting this breaks the GPT surface — only that the shipped text is factually stale relative to what the server now returns, and that this directly contradicts the "BOTH surfaces" completeness claim ledger 92 makes. It's exactly the kind of drift a systems/consistency pass should catch even when the functional risk is likely low.

**Fix**: swap the stale example in §10.2b's NEW block: `"Missing required fields: story_card"` → `"Missing required fields: Story"`, and simplify/drop the now-redundant translation parenthetical `(story_card = the story, headline = the tagline)` since the server-side label is already plain. This is **byte-negative** (`story_card` → `Story` alone saves 5 bytes), so it improves the `.txt`'s 12-byte headroom rather than threatening it — no re-budgeting risk, just re-run the Phase 10.5 `wc -c` recount as the doc already requires after any instruction edit.
