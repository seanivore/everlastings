## Findings

### 1. [LOAD-BEARING] Two live customer-facing pages still promise the removed 15-minute cart hold — WS7 §7.2's `cart_holds` removal never names or touches them

**Where**: `policies.html:167–172` (a dedicated section, `<section id="cart-hold"><h2>The Cart Hold</h2>`) and `faq.html:192–195` ("How does the cart work?"). IMPLEMENT.md WS7 Phase 7.2 (all of 7.2a–7.2i) + its Doc-impact line (~2817) + the C#1 go-live note (ledger 78).

**The systems seam.** WS7 §7.2 correctly and surgically removes every `cart_holds` read/write from `api/checkout.ts` + `api/webhook.ts` (verified byte-for-byte against the live tree — every CURRENT anchor I checked matches). Its Doc-impact note (folded at v3.7.2, C#1) is scoped entirely to `EVERLASTINGS_STORE.md` — the internal architecture doc. But two **public, customer-facing** pages independently describe the removed mechanism as current, active store behavior, and neither is named anywhere in WS7, the C#1 fold, or the go-live note:

- `policies.html`'s own dedicated "**The Cart Hold**" section (distinct from the adjacent, still-accurate "Availability & Cart" section right above it) reads: *"When you click Checkout from your cart, we place a soft 15-minute hold on the pieces you've chosen. **That hold means no one else can claim them** while you're entering your shipping and payment details."* / *"If you step away for longer than 15 minutes, the hold quietly releases... This is the gentlest version of 'first come, first home' we could find."*
- `faq.html:194` repeats the claim inline: *"We verify availability when you click Checkout and **place a 15-minute soft hold** while you enter shipping and payment."*

After WS7 ships, both statements are **factually false**. `handleReserve` becomes a pure availability check with no hold side-effect — a second shopper genuinely **can** claim (and pay for) the same qty-1 piece while the first is mid-checkout, which is the *exact* scenario `policies.html` explicitly promises can't happen. This is not a hypothetical edge case; it is precisely the "two-shopper race on a one-of-a-kind piece" that the C#1 go-live note (ledger 78) already reasons through and accepts as a low-volume trade-off (`record_sale` never oversells; a rare double-pay recovers via a normal refund). The build's own architecture record has fully accepted this race can happen — but nothing connects that acceptance to the fact that a still-live public page makes a specific, dedicated, branded promise that it cannot. I confirmed this isn't a broader false-positive: `about.html`'s "held still" hit is unrelated brand prose (grief/memory metaphor, not cart mechanics); `data-flow.md` (the design contract doc) never mentions hold/reservation at all; `GPT_SETUP.md`/`STORE_ADMINISTRATION.md` don't mention `cart_holds` either, so they need no companion edit. `policies.html` and `faq.html` are the only two customer-facing hits in the whole repo, and both are complete misses in this build.

**This is a genuinely new finding, not a re-raise of ledger 78.** Ledger 78 closed the `EVERLASTINGS_STORE.md` documentation angle (KAD #18/19, schema, API map, table count, the go-live note) — its own location list never mentions `policies.html` or `faq.html`, and neither does any workstream in the 3739-line IMPLEMENT.md. This is the shopper-facing sibling of that same fold, sitting entirely outside every workstream's stated file scope, which is exactly the class of gap a systems-breadth pass (vs. a per-workstream fidelity pass) is positioned to catch.

**Fix**: add a bullet to WS7 §7.2's Doc-impact (and the `EVERLASTINGS_STORE.md` go-live checklist entry the C#1 fold already added) naming both files. `policies.html`'s adjacent "Availability & Cart" section already states the accurate post-build behavior almost verbatim ("it is not reserved... we verify availability... when you begin checkout") — the fix is to retire/rewrite the separate "The Cart Hold" section (167–172) rather than invent new copy, and trim `faq.html:194`'s "place a 15-minute soft hold" clause to match. Small, mechanical, cheap — but it has to be a named build step; nothing in the current doc surfaces it.

### 3. [POLISH] The same Doc-impact's "correct the is_test '8 core tables → 7' count" doesn't match any literal STORE.md passage — it conflates two separately-worded, differently-scoped counts

**Where**: IMPLEMENT.md §7.2i Doc-impact (~line 2817); `EVERLASTINGS_STORE.md` line 140 (`Tables (8):` in the System Diagram's table list) vs. line 1142 (**"`is_test` isolation (all six core tables)"** — a *different*, smaller count, which separately enumerates by name: "`products`, `customers`, `orders`, `subscribers`, `product_interests`, and `cart_holds`").

**The systems seam.** STORE.md never contains the string "is_test... 8 core tables" anywhere — I grepped for it directly. The 8-count (System Diagram, line 140) and the 6-count (the is_test-isolation paragraph, line 1142) are two distinct facts about two different things: the System Diagram counts *all* Supabase tables (8, including `site_config` and `webhook_events`, which the very next sentence in that same paragraph explicitly says do **not** carry `is_test`); the is_test paragraph counts only the tables that *do* carry the flag (6, a strict subset). Removing `cart_holds` changes the first count 8→7 **and** the second count 6→5 — two separate edits in two separate places, each of which also needs `cart_holds` dropped from its own explicit name-list (the is_test paragraph's list currently names it directly). The Doc-impact's single, blended phrase doesn't literally match either passage, so a doc-sync pass searching for it could plausibly edit only the more prominent "Tables (8)" line and miss the "all six core tables" paragraph's own separate count and its own explicit `cart_holds` mention.

**Fix**: split into two named edits — "`Tables (8):`" → "`Tables (7):`" (System Diagram — also drop the `cart_holds` row from the ASCII table list at lines 140–148) **and** "all six core tables" → "all five core tables" (the is_test paragraph — also drop `cart_holds` from its enumerated list of table names).
