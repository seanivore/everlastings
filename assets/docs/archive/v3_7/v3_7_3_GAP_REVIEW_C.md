**4. [LOW / polish, flag-not-assert — low reachability] A null-`quantity` + `available:true` row is a genuine but hard-to-reach 4th-enforcer disagreement, distinct from the already-covered stale-quantity legacy case.**
- **Systems seam**: the delivered (unowned-by-this-build) `computeState()` (`design-handoff/out/products-app.js:20`, `p.quantity === 0` strict equality) vs. WS6's new null-aware storefront gate (`p.quantity != null ? p.quantity <= 0 : !p.available`) vs. the server checkout gate (`quantity >= 1`, which is `false` for `null` under JS numeric coercion).
- **Traced per the charge**: a real `quantity:0` sold piece — all four enforcers agree (Sold/unbuyable) cleanly, no contradiction. A **null**-quantity, `available:true`, published row: `computeState()` falls through past its `quantity === 0` check (strict equality, `null !== 0`) to `"live"` — the portal shows it fully Live, no warning. The storefront's null-fallback reads `!p.available` = `!true` = `false` → also shows it as a normal buyable tile. But the server gate's `quantity >= 1` is `false` for `null` → checkout silently 410/409s. Em sees zero indication in her portal that the piece can't actually sell — the one case where "nothing hides without explaining" would be violated by this trace.
- **Reachability (why this is polish, not load-bearing)**: WS2 §2.7's new `validatePublishRules` requires non-null `quantity` to publish, and the PUT handler's quantity guard already rejects a non-integer (including `null`) `quantity` with a 400 — so a **normal** create→publish→edit lifecycle under this build's own rules can never produce this row. It's reachable only via a direct Supabase Studio write bypassing the API (already discouraged elsewhere in STORE.md), and the catalog is currently empty (ledger 66/71) so no such legacy row exists today. This is a distinct case from the already-documented and backfill-covered "stale non-null quantity + `available:false`" edge (§6.5's explicit callout, fixed by the `20260616000001` backfill) — that backfill's verification query (`quantity > 0 AND available = false`) would **not** catch a null-quantity row.
- **Fix (optional, non-blocking)**: either extend the go-live backfill verification to also assert zero rows match `quantity IS NULL AND is_published = true`, or simply note the edge case alongside the existing one in §6.5's legacy caveat. `computeState()` itself is out of this build's stated scope ("no client change"), so no code fix is being requested — just a one-line acknowledgment so it isn't rediscovered cold at go-live.
