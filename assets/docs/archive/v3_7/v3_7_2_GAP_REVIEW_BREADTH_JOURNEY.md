## Finding 1 — [LOAD-BEARING] The v3.7.1 checkout-identity-freeze fix (§2.7a) closed the server/data-integrity half of the "pause → edit → relist" bug, but never closed the client-side half — the editor and the media modal still show `checkout_name`/`checkout_description`/`checkout_image` as unlocked on a paused piece, and no instruction anywhere surfaces the 400 that now results

**Journey it breaks:** "Put a piece back up for sale" (Available OFF→ON round-trip) and, secondarily, "Media upload modal" (the `checkout_image` role specifically) — the same two journeys ledger 73/75 already touched. This is NOT a re-raise of the closed Stripe-desync bug (breadth journey #1, v3.7.0) — that specific failure mode (silent DB↔Stripe drift) is genuinely closed. This is the other half of that same original finding's recommendation, which was never implemented.

**Where:**
- `v3_7_2_IMPLEMENT.md` §2.7a (~line 925), the actual NEW server code — confirmed correct and complete: it hoists the `FROZEN_AFTER_PUBLISH` rejection to fire on `current.published_at` (ever-published) instead of `current.is_published` (currently-published), and preserves `published_at` on relist. This is genuinely fixed, server-side.
- `v3_7_0_GAP_REVIEW_BREADTH_JOURNEY.md` Finding 1's own "concrete fix" paragraph (the source of ledger 73) named **three** things to fix: (1) the server `FROZEN_AFTER_PUBLISH` guard, (2) "the **client** 'locked' checks (the editor's `published` var…)", (3) "…**the media modal's checkout-role lock**" — instead of `is_published`. Only (1) shipped. (2) and (3) are absent from §2.7a and from every other phase I read.
- `v3_7_2_IMPLEMENT.md` §5.4c/5.4e (~lines 2010, 2033) — Phase 5.4e's own text still reads **"on a `published` product the modal must (i) show the 'checkout' checkbox as locked… and (ii) not include `checkout_image` in the Apply `PUT`"** — the exact ambiguous word ("published," not "ever-published") that caused the original bug, and it still cites the pre-fix guard location (`products.ts:398-409`) rather than the new pre-branch location §2.7a actually inserted.
- `v3_7_2_ADDENDUM_DESIGN.md` §A, "Surgical edits to the shipped files (**the ONLY diffs; everything ELSE is verbatim**)" (~line 38) — the enumerated list (WS1 robots/auth, WS2 `product_type` picker, WS8 Sold-tab alert, WS3 Delivered pill, the `--staged` token fix, WS1 View-Site href) does **not** include updating `products-app.js`'s `published` lock-condition variable. Per this section's own stated discipline, a builder must NOT touch that variable unless it's on this list — so the fix Finding-1 asked for is not just unlikely to be inferred, it is **actively excluded** by the doc's own byte-fidelity rule as currently written.
- `v3_7_2_ADDENDUM_TESTING.md` WS2 item 6 ("Freeze — v3.7.1 §2.7a") (~line 40) — tests only that the SERVER 400s when you try to edit a frozen field on a paused piece; it never asserts the field renders **locked before you even try** (the UI-legibility half). This is corroborating evidence, not a separate gap: the test only covers what the fix actually did.

**Concrete failure scenario:** Emaline publishes a piece, later pauses it (Available OFF — an ordinary, encouraged action). While paused, she opens the row editor. Because the client's `published` variable is still `p.is_published` (now `false`), `checkout_name`/`checkout_description` render **unlocked** — no lock icon, no "Locks after first publish" tooltip, indistinguishable from a field that's actually editable. She edits `checkout_description` (or, via the media modal, re-roles a different photo as `checkout_image` — a workflow §5.4c explicitly built a re-upload mechanic for). Because a paused piece is NOT staged (per the doc's own "staged edits if published" rule, an unpublished/paused row writes straight through), the autosave-on-close fires a `PUT` immediately. §2.7a's server guard now correctly rejects it — `400 "Frozen after publish: checkout_description…"` — but **no phase in the doc instructs how/whether that 400 is surfaced**. Contrast this with the `commitAvail`-ON seam, which the WS2 integration-seam table explicitly calls out: *"an under-filled piece can 400 here… **SURFACE it as a field-list toast, not a silent no-op**"* — that explicit instruction exists for one flow and not this one, which is why I'm reading its absence here as a real gap rather than an assumed catch-all.

**The media-modal amplification (needs-verification, not asserted):** if the modal's Apply diff (§5.4c.i) also treats the "checkout" role as unlocked on a paused piece and includes `checkout_image` in the terminal `PUT {images, media, thumbnail, seo_thumbnail, checkout_image}`, the WHOLE terminal PUT would be rejected by the same freeze guard — potentially blocking an otherwise-legitimate gallery reorder or re-role made in the **same** Apply session, since the doc's partial-failure recovery language (§5.4c.i) only describes what happens when a per-item upload POST fails, never what happens when the terminal PUT itself 400s. I can't verify from the docs alone whether this compounds into "the whole Apply silently does nothing" or "just the checkout role is lost" — flagging it needs-verification because it depends on code I can't see, not asserting it's broken.

**Why this isn't a re-raise:** ledger 73 explicitly closes "the pause→edit→relist Stripe-desync" and "the `published_at` re-stamp" — both of those are genuinely fixed and I'm not re-opening them. This finding is about the UI-legibility half of the SAME original recommendation, which was never attempted and is a distinct, still-open risk: a maker sees an editable-looking field, acts on it, and gets an unexplained rejection — exactly the "reads as it just didn't work and didn't say why" failure class this review lens exists to catch, just no longer with silent data corruption behind it.

**The fix:** (a) add one line to DESIGN §A's surgical-edits list: introduce an `everPublished = !!p.published_at` (or equivalent) client variable and re-key the `locked:` flags for `checkout_name`/`checkout_description` off it instead of `published` — leave `product_type`/`slug`'s existing locked-conditions alone (they're governed by separate, pre-existing, unrelated immutability rules, not `FROZEN_AFTER_PUBLISH`, so they're out of this finding's scope); (b) update §5.4e's text (the media modal's checkout-role lock) to the same `published_at`-based condition and correct its stale `:398-409` reference; (c) add an explicit toast/surface instruction for a rejected autosave PUT on the editor (mirroring the `commitAvail`-ON seam's explicit language), and confirm what the media modal's Apply does when the terminal PUT itself 400s.
