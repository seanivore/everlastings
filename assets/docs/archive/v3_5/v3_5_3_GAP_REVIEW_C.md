## Part 1 — Scoped findings (ranked)

**C-R3-1 — [needs-verification · low · fail-safe · fix-already-in-repo] A *legacy* pre-v3.3 sold piece can render struck-priced on the storefront if the one-time cutover backfill isn't run.**
- Location: WS6 §6.5a/§6.3d/§4.5.d merged card blocks vs. `supabase/migrations/20260616000001_v3_1_inventory_decrement.sql:1-21`.
- The merged blocks make `sold = p.quantity != null ? p.quantity <= 0 : !p.available`. For a *genuinely-sold v3.3+ piece* (`record_sale` → `quantity=0`, `available=false`) this is fully consistent across all enforcers — see Part 2, no leak. But a **pre-v3.3 sold piece was never quantity-decremented**, so it sits at `available:false, quantity:1` (the migration's own comment, lines 1-2). For that row the quantity-primary branch computes `1 <= 0 → sold=false` → the tile renders **struck price + "One of a kind" badge + `data-available=true`** (and the PDP sticky renders struck), where the pre-build code (`p.available`) correctly rendered **"Sold" + plain**. It still **fails safe on *buyability*** — the server checkout/reserve gate (`checkout.ts:79`/`:205`, `available !== true` → 410) blocks the purchase, and struck pricing is a brand-new surface so this is a display artifact, not a buy leak (buy-leak is settled by ledger 33b).
- Why it's live-relevant: the fix exists — the migration's cutover UPDATE (`set quantity = 0 where available=false and quantity>0 and exists(orders)`) aligns exactly these rows — but it **ships commented / run-by-hand** (AR#C-R2-1) and **is not referenced or sequenced anywhere in this build's IMPLEMENT or TESTING addendum** (IMPLEMENT:77 explicitly hands the go-live cutover to a separate ROADMAP-A runbook). So a builder/operator following only the v3.5.3 package has no prompt to run it before the struck-pricing layer goes live.
- Concrete fix (pick one, both cheap): (a) add a one-line go-live/testing step "run the `20260616000001` cutover SELECT→UPDATE once before enabling any `%` sale, to zero legacy sold rows' stock" to the TESTING addendum's Stripe-prerequisites / deploy block; or (b) explicitly note in §6.5a that legacy `available:false, quantity:1` rows depend on that backfill for correct grid display (buyability already fails safe). Flag, not assert: whether any such row exists in Emy's actual catalog is unverifiable from here — if every sold piece is post-v3.3 (`quantity` already 0) the risk is nil.

No other scoped finding. The card-render merge, the enforcer naming, the orders-signal payload, the `?code=` wiring, and the function/cron budget are all clean (Part 2).
