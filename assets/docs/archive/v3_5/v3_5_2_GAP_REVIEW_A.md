## Ranked findings (most likely to derail first)

### 1. [HIGH] The coupon "Copy share link" never reaches the checkout reader that honors it (WS4 §4.6 ↔ §4.7)
**Where:** §4.6 (share-link construction) + §4.7 (`applyShareLinkCode` in `checkout.js`).
**What's wrong:** §4.6 builds the share link as `((D.config && D.config.siteUrl) || 'https://everlastingsbyemaline.com') + '/?code=' + encodeURIComponent(code)` — i.e. the **site root** (`/?code=`). The only reader, §4.7's `applyShareLinkCode`, runs in `checkout.js` on the **checkout page** and reads `new URLSearchParams(location.search).get('code')`. A shopper who clicks the share link lands on the **homepage** (`/?code=`), where `checkout.js` does not run; by the time they add items and reach `/checkout`, the `?code=` param is gone. Nothing in the two phases captures/persists the code between landing and checkout (main.js's `DOMContentLoaded` in §4.3.b mounts sale chrome but never reads `?code=`). As authored, the share link is silently a no-op — the discount is never applied.
**Note (flag-don't-assert):** even if `checkout.js` were loaded elsewhere, the homepage has no `#promo-code` field and no mounted `checkout` object, so `applyShareLinkCode` still can't apply. Ledger 30 SETTLES the *intent* ("WS4 adds a checkout.js prefill+apply so the link is honored") — this finding is that the §4.6/§4.7 wiring as written does not deliver `?code=` to that reader, not a re-litigation of whether to honor it.
**Concrete fix:** capture `?code=` site-wide — in `main.js` (loads on every page) read `?code=` on load and stash it (`sessionStorage.setItem('everlastings.shareCode', code)`), then have `applyShareLinkCode` read the stash with `location.search` as a fallback. (Or repoint the share link at a path where the reader runs — but a bare `/checkout?code=` with an empty cart is wrong, so the site-wide stash is the correct fix.)

**Where:** §4.5.b + §6.5a (`shop.js` card price); §4.5.f + §6.3d (`homepage.js` `populateFeatured`); §4.5.d vs §6.5b (`product.js` sticky price, semantic only).

Also extend TESTING item 30's "verify both landed without clobbering each other" to include struck-pricing survival, not just WS6↔WS9.

### 3. [MEDIUM] Struck checkout total assumes `getCartTotal()` (and cart's `getCart()`) are available where they're called (WS4 §4.4.a, §4.5.g)
**Where:** §4.4.a (`checkout.js` `change` listener) uses `getCartTotal()`; §4.5.g (`cart.js`) uses `getCart()`.
**What's ambiguous:** §4.5.i shows `getCartTotal()` used inside `cart.js`, and §4.4.a calls it inside `checkout.js` — but the doc never establishes that `getCartTotal` (or `getCart`) is a **shared/global** helper (e.g. in `main.js`) rather than a `cart.js`-local. If `getCartTotal` lives in `cart.js` and `cart.js` isn't loaded on `/checkout`, the `change` listener throws a ReferenceError and the checkout total never renders (more than cosmetic — it can break the listener). §4.5.g's `getCart()` in the `.then()` closure is the same question (the CURRENT context there uses an in-scope local `cart`, so `getCart()` is a newly-introduced reference the doc doesn't anchor).
**Concrete fix:** name the shared home of `getCartTotal`/`getCart` (confirm they're in `main.js` and therefore present on `/checkout`), or in §4.5.g reuse the in-scope `cart` local instead of `getCart()`. NEEDS-VERIFY against the repo, but the doc should state where these live so a cold builder doesn't guess.

### 5. [MEDIUM] A scheduled-publish on an incomplete draft fails silently, counter to "nothing hides without explaining" (WS2 §2.4/§2.6)
**Where:** §2.6 `publishDueScheduled` + §2.4 (what arms `scheduled_publish_at`).
**What's wrong:** `publishDueScheduled` calls `?_action=publish`, which runs the full `validatePublishRules`; an incomplete scheduled draft **400s and is logged+skipped** (best-effort, correct for robustness). But nothing surfaces that failure to the maker, and the doc's stated rule for *when* to offer Schedule keys off "a publish is pending" (an unpublished draft, or a published row with staged edits) — which is orthogonal to "passes the required-field gate." So a maker can schedule a piece that is missing required fields; the cron silently never publishes it, and she gets no explanation — the exact "hides without explaining" failure the thesis forbids. (The §2.4 NEEDS-VERIFY about hiding Schedule on a *clean published-no-draft* row is adjacent but does not cover the incomplete-draft case.)
**Concrete fix:** gate the Schedule control on **publish-readiness** — the surface's `readiness()`/`refreshGate()` already computes whether the piece passes the gate; only offer Schedule when it does (so a scheduled piece always publishes at cron), and/or add a maker-facing notice when a scheduled publish fails validation.
