## Findings (ranked · both low-priority · neither blocks the build)

**C1 — The "three enforcers" framing omits a FOURTH: the server checkout/reserve gate still uses `available===true` AND-logic, not the storefront's quantity-primary gate. (Low; fail-safe; needs-verify only as a UX note.)** §6.5 makes the storefront *display* gate quantity-primary (`quantity != null ? quantity<=0 : !available`), but the server buy path (`checkout.ts:79` session + `:205` reserve) keeps `available !== true || (quantity ?? 0) < 1` — i.e. it requires `available===true` AND `quantity>=1`. This is the correct fail-safe direction (server stricter → no oversell, no sold-leak — the mandate's core question passes), and after WS2 §2.2 (available-off → unpublish) the anomalous rows that could diverge are largely unreachable via the UI. The residual edge is display-vs-checkout UX on *legacy/anomalous* rows: a published row with `quantity>0 & available===false` renders buyable on the storefront but 410s at checkout; a published row with `quantity=null & available===true` renders buyable but the server treats `(null ?? 0) < 1` as unavailable. Both are pre-existing (today's storefront already gates on `available` only, and checkout already required `quantity>=1`) — §6.5's null-fallback *preserves* rather than introduces them — and both fail safe. Suggested one-line confirm: either state in the IMPLEMENT that the server checkout/reserve gate is the intentional strict 4th enforcer (so a reviewer doesn't read "three enforcers" as exhaustive), or note that products always carry a non-null `quantity` (schema DEFAULT 1) so the null branch is dead for API-created rows.

**C2 — `refreshOrdersSignal` does an unbounded full-`orders` read (with product+customer joins) on EVERY portal page load, only to read one scalar. (Low; single-admin-acceptable perf note.)** `GET /api/orders` with no `status` param returns the entire `orders` table joined to `products`+`customers` (`orders.ts:63-101`), and §8.3 fetches it on every `mountShell` page plus the Products landing purely to read the server-computed `unseen_count` and client-count needs-shipping. On the Orders page this is a second fetch on top of the surface's own list load. For v3.5 single-admin / low volume this is fine, but the payload grows with order history and is fetched per nav. Optional tightening (not required to ship): pass `?status=needs_shipping` (the needs count is then `orders.length` and `unseen_count` still returns regardless), or expose a lightweight count-only branch. Flagging as an efficiency note, not a correctness gap.
